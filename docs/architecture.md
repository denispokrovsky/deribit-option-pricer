# Архитектура {#architecture}

## Обзор

Программа — конвейер Unix-стиля: каждый шаг читает stdin и пишет stdout, поэтому шаги можно
заменять и комбинировать.

```
 Deribit REST API
       │  scripts/fetch_deribit.py          (Python, FR-7)
       ▼
 quotes.csv ──► dp_cli ──► result.csv ──► scripts/load_results.py ──► SQLite ──► sql/reports.sql
             (C++, FR-1..6)                    (Python, FR-8)                   (SQL, FR-8)
```

Внутри `dp_cli` код разделён на слои; зависимости направлены только вниз:

```
apps/dp_cli.cpp            CLI: аргументы, stdin/stdout, коды возврата
      │
quote_pricer               Сервис приложения: котировка Deribit → IV + греки
      │
 ┌────┴──────────────┬───────────────────┐
quote_csv          instrument        implied_vol ──► black76
(адаптер CSV)   (имена Deribit)     (стратегии IV)    (модель, чистые функции)
```

| Модуль | Ответственность | Знает о Deribit? | Ввод-вывод? |
|--------|-----------------|------------------|-------------|
| `black76` | Цена и греки по формулам Black-76 | нет | нет |
| `implied_vol` | Обратная задача: цена → волатильность | нет | нет |
| `instrument` | Разбор `BTC-27DEC24-60000-C`, расчёт срока | да | нет |
| `quote_csv` | Разбор строки CSV в `OptionQuote` | да | нет (строки) |
| `quote_pricer` | Склеивает всё выше, форматирует результат | да | нет (строки) |
| `dp_cli` | Потоки, аргументы, диагностика | нет | да |

Ядро (`black76`, `implied_vol`) не зависит ни от формата данных, ни от биржи, поэтому его легко
тестировать и использовать повторно, например для другой биржи.

## Паттерны проектирования

- **Strategy** — `ImpliedVolSolver` с тремя реализациями. Алгоритм выбирается во время выполнения
  (`--solver`), а тесты и бенчмарк прогоняют все реализации одинаково.
- **Factory** — `makeSolver(name)` скрывает конкретные классы от CLI; добавление нового метода
  не меняет `dp_cli.cpp`.
- **Adapter** — `quote_csv` и `instrument` переводят соглашения Deribit (CSV-колонки, имена
  инструментов, котировка в монете, экспирация в 08:00 UTC) во внутренние типы.
- **Application service** — `priceQuote()` — единственное место, где встречаются модель и соглашения
  биржи. Результат — `std::variant<PricingResult, PricingError>`: ошибка — обычное значение, а не
  исключение, потому что неподходящая котировка (истёкший опцион, цена вне границ) — штатная ситуация.
- **Pipes and filters** — на уровне всей системы: Python → C++ → Python → SQL через потоки.

## Выбор решения: алгоритм поиска IV (FR-3)

Задача: найти σ, при которой `price(σ) = рыночная цена`. Функция монотонно растёт по σ,
но около нуля и при больших σ почти плоская (vega → 0), особенно для опционов далеко от денег
и с коротким сроком — а именно такие преобладают на доске Deribit.

### Рассмотренные варианты

| Вариант | Скорость | Надёжность | Сложность |
|---------|----------|------------|-----------|
| **A. Бисекция** на [1e-6, 10] | ~37 итераций до 1e-10 | Всегда сходится, если корень в интервале | Минимальная |
| **B. Ньютон** с начальной точкой Манастера–Келера | 3–6 итераций | Без защиты может уйти в σ ≤ 0 или NaN при vega ≈ 0, на ценах около границ арбитража | Низкая |
| **C. Ньютон в сужающемся интервале** (safeguarded Newton) | Как B на «хороших» опционах | Как A: шаг, выходящий из интервала, заменяется шагом бисекции | Средняя |
| **D. «Let's Be Rational»** (P. Jäckel, 2015) | 2 итерации, машинная точность | Максимальная | Высокая: ~1000 строк, рациональные аппроксимации |

### Обоснование выбора: C

1. **Надёжность — обязательное требование.** Неудача поиска IV означает потерянную строку в отчёте (TR-P2:
   не более 1% неудач). Вариант B этого не гарантирует, C — гарантирует тем же аргументом, что и A:
   корень всегда остаётся внутри интервала, который только сужается.
2. **Скорость с запасом.** Требование TR-P2 — 5 мкс; C тратит столько же итераций, сколько B,
   а одна итерация Black-76 стоит десятки наносекунд. Числа видны в журнале CI:
   бенчмарк `BM_ImpliedVol` прогоняет A, B и C на одной цепочке из 1000 опционов и показывает
   время, среднее число итераций (`avg_iterations`) и долю неудач (`failure_rate`).
3. **Вариант D избыточен.** Он даёт выигрыш в единицы микросекунд, который не нужен ни одному
   требованию, ценой большого и трудного для проверки кода. Благодаря паттерну Strategy его можно
   добавить позже, не трогая остальную программу.

A и B оставлены в коде как эталоны для сравнения в тестах и бенчмарке.

## Выбор решения: хранилище результатов (FR-8)

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| CSV-файлы | Ноль зависимостей | Нет запросов, анализ только скриптами |
| **SQLite** | Встраиваемая, один файл, полноценный SQL; модуль `sqlite3` есть в стандартной библиотеке Python | Один писатель одновременно |
| PostgreSQL | Многопользовательский доступ | Нужен сервер: усложняет запуск «в другом окружении» (TR-6) |

Выбран **SQLite**: даёт SQL без сервера и без новых зависимостей у C++-кода. Запись вынесена в
Python-скрипт, поэтому `dp_cli` остаётся простым фильтром stdin → stdout.

## Соглашения Deribit, учтённые в модели

- Форвард — поле `underlying_price` котировки (цена фьючерса или синтетический форвард этой экспирации).
- Цена в USD = `mark_price` × `underlying_price`; ставка дисконтирования = 0.
- Срок — ACT/365 от момента котировки до 08:00 UTC даты экспирации.

На снимке из `data/btc_options_sample.csv` (880 опционов) медианное расхождение нашей IV с `mark_iv`
составляет ~0,004 пункта волатильности. Заметные расхождения только у глубоко ITM опционов с
экспирацией через 1–2 дня: их цена почти равна внутренней стоимости и округлена до шага цены
биржи, поэтому IV там плохо обусловлена — это свойство данных, а не ошибка модели.
